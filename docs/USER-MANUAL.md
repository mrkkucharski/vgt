# vgt user manual

vgt prepares an existing REAPER project for guitar practice. It analyzes one
reference mix, optionally separates practice stems through LALAL.AI, makes
local reference MIDI from those stems, and adds only its own objects to the
project.

## Quick workflow

1. Install the CLI and the REAPER actions:

   ```sh
   uv tool install git+https://github.com/mrkkucharski/vgt.git
   vgt install-reascripts
   ```

   Actions go to `~/Library/Application Support/REAPER/Scripts/vgt`. Register
   these seven once with `ReaScript: Load` in REAPER's Action List:
   `vgt_initialize.lua`, `vgt_sync.lua`, `vgt_sync_tempo_map.lua`,
   `vgt_create_working_copy.lua`, `vgt_promote_working_copy.lua`,
   `vgt_transcribe_track.lua` and `vgt_get_transcription.lua`.
   (`vgt_common.lua` is a shared library, not an action.)
   `install-reascripts` takes `--dry-run`, `--destination DIR`, and `--force`
   to replace a changed file without asking.
2. Save the project `.RPP` in REAPER 7.x.
3. Run `vgt_initialize.lua`. On first use, pick a file-backed reference track
   and declare its guitar electric or acoustic. This writes a `Song.vgt`
   sidecar and creates the `[clean]`, `[work]` and `[vgt]` containers.
4. Run `vgt analyze "Song.RPP"` in a terminal. It analyzes the mix, separates
   stems, and transcribes the requested stems (guitar by default).
5. Run `vgt_initialize.lua` again to import analysis, stems and reference MIDI.
6. Correct what you need (see [Corrections](#corrections)).
7. Inspect state with `vgt status "Song.RPP"` (add `--json` for machine
   output).

`vgt [project.rpp]` and `vgt inspect [project.rpp]` are read-only. Without a
path, vgt uses the only `.RPP` in the current directory and refuses to guess
otherwise. vgt never text-edits an RPP; all project changes go through the
REAPER actions.

## Objects vgt creates in REAPER

Original tracks, items and regions are never changed. At the bottom of the
project, initialize keeps this order: loose root tracks, `[clean] <reference>`,
`[work] <reference>`, `[vgt] <reference>`, then `[vgt] MT3` when present. The
workflow runs bottom-up: vgt generates into `[vgt]`, you copy into `[work]` to
edit, then promote into `[clean]` to keep.

| Object | When | Purpose |
| --- | --- | --- |
| `[clean]`, `[work]` | Initialization | User-content containers for finished and in-progress tracks. vgt may create, rename, recolour and move the container track, never its contents. |
| `[vgt] <reference>` | Initialization | Folder for everything vgt generates. |
| `[vgt] Chords`, `[vgt] Key` | Chord / key analysis | Silent text-item machine drafts, regenerated by every analyze and apply. Copy to `[work]` to correct. |
| `[vgt] Beats` | Tempo analysis | Silent, locked beat items. Never turned into project tempo markers. |
| `[vgt] Click` | Tempo analysis | Muted click audio; unmute to check the beat grid. |
| Vocals, Instrumental, Bass, Drums, Guitar, Backing | Stem separation | Time-based audio stems. |
| Strings, Keys / Piano | Explicitly requested | Optional time-based stems. |
| `[vgt] <Target> Ref — <Label> (MIDI)` | Transcription variant | One MIDI item per retained variant, directly under its stem, spanning the reference. Unmuted but silent until you load an instrument. |
| `[vgt] MT3` | `vgt analyze --mt3-review` | One MIDI track per MT3-predicted instrument. Unfiltered review candidates. |
| Section regions | Section analysis | Movable, renamable section markers. |

An empty `[clean]` or `[work]` shows as a plain track until it gets a child;
REAPER has no empty folders. Containers are coloured once when created
(`[clean]` yellow-green, `[work]` light blue, `[vgt]` mauve); a manual
recolour is kept. Ownership is tracked by provenance, not colour.

## Analysis

`vgt analyze` detects the tempo/beat grid, key, sections, and beat-aligned
major/minor chords. Instrumental, guitar and backing stems also inform chord
detection once available. Detected sections are a draft; see
`docs/section-detection-findings.md` for the method and limits.

Artifacts live under `vgt/<stable-id>/` beside the project:

- `tempo-click.wav`, `chords.txt`, `sections.txt`.
- `stems/*.wav` — separated stems.
- `transcription/<target>/<variant-id>.mid` and `.csv` (drums: `.json`) — each
  retained variant's reference MIDI and note or event data.
- `transcription/cache/<backend>/<hash>/` — shared raw detection; variants
  that differ only in cleanup reuse it.
- `mt3/` — the MT3 review output.

Moving the project folder keeps everything portable.

## Corrections

**Chords and key.** `[vgt] Chords` and `[vgt] Key` are regenerated on every
analyze and apply. To keep a correction, select the track, run
`vgt_create_working_copy.lua`, edit the `[work]` copy, then run
`vgt_promote_working_copy.lua` to move it into `[clean]`. A key copy needs one
item named like `E minor` or `F# major`; chord items can be renamed, moved,
split, deleted or added.

**Sections.** Rename or move the vgt section regions, then run `vgt_sync.lua`.
The edits become human-verified; the detected baseline is kept. Applying
before syncing discards unsynced region edits.

**Tempo.** vgt shows its beat grid only on `[vgt] Beats` and never writes
project tempo or time-signature markers. To adopt a REAPER tempo map you
corrected yourself, run `vgt_sync_tempo_map.lua` and confirm. It reads the
markers over the reference item only (constant or piecewise; linear ramps
are rejected) and stores them as the human-verified grid used by later
transcription and chord analysis. `vgt analyze --force` refreshes only the
detected baseline. To go back to the detected tempo, copy
`analysis.tempo.detected` over `analysis.tempo.value` in the sidecar, set
`human_verified` to `false`, and run `vgt_initialize.lua`. This is manual on
purpose, so a verified correction is never silently discarded.

## Stem separation and cost

Separation uses the LALAL.AI API v1. Set `LALAL_LICENSE_KEY` in your
environment; never put it in a sidecar, command or log. There is no offline
separation.

`vgt analyze` attempts any missing standard separation. Use `--no-stems` for a
free, mix-only run. The standard recipe is five paid operations:

| Source split | Kept artifact(s) |
| --- | --- |
| Mix: vocals | `vocals`, `instrumental` |
| Mix: bass | `bass` |
| Mix: drums | `drums` |
| Mix: electric/acoustic guitar | `guitar` |
| `instrumental`: electric/acoustic guitar | `backing` (no guitar) |

```sh
vgt analyze --guitar electric "Song.RPP"
vgt analyze --guitar electric --extra-stem strings --extra-stem keys \
  --accept-stem-cost "Song.RPP"
```

- `keys` and `keys/piano` are aliases for `piano`. Optional stems are never
  part of the standard recipe.
- `--force` refreshes local analysis only and never spends credits.
- `--force-stems` repeats paid work, showing operation count, balance and
  duration estimate before confirming.
- Non-interactive paid refreshes and optional stems require
  `--accept-stem-cost`.

vgt checkpoints operations, validates WAVs before caching, and resumes
interrupted work instead of resubmitting it.

## Stem transcription (reference MIDI)

Transcription runs locally inside `vgt analyze`, after separation. It is free
and needs no confirmation. A target with no stem is skipped; vgt never falls
back to the full mix.

| Target | Default backend |
| --- | --- |
| `guitar` | Essentia Klapuri (`guitar-klapuri`) |
| `bass` | pYIN pitch tracker |
| `drums` | DrumScript on the raw stem (`raw`) |
| `vocals`, `instrumental`, `backing`, `strings`, `piano`, `original` | Basic Pitch |

**No fallback.** If a backend fails, that target records an error and the
rest of analysis continues. vgt never substitutes another backend.

**Drafts.** Every transcription is a draft reference to correct by ear, not
ground truth. MIDI has no string or fret information, so there is no
tablature.

Flags for `vgt analyze`:

- `--transcribe <target>` adds a target to the persisted set (guitar is in it
  by default). Targets: `guitar`, `bass`, `vocals`, `drums`, `instrumental`,
  `backing`, `strings`, `piano`, `original` (the mix).
- `--transcribe-only <target>` runs just that target this time.
- `--forget-transcription <target>` removes a target and its artifacts.
- `--no-transcribe` skips transcription this run, including `--mt3-review`.
- `--mode <target>=<profile>` sets a target's default profile, e.g.
  `--mode guitar=guitar-acoustic` or `--mode drums=hpss`.
- `--mt3-review` also runs MT3 over the instrumental stem and keeps every
  predicted instrument as its own track in the `[vgt] MT3` folder. Off by
  default; needs [provisioned MT3](#mt3-provisioning).
- `--forget-mt3-review` deletes the MT3 review; the next apply removes the
  folder.

`--guitar electric|acoustic` affects LALAL separation only, not the
transcription profile.

`vgt status` lists each target's retained variants with profile, note count
and pitch range (drums: per-instrument event counts), plus any skip or error:

```text
transcription: 1 target, 2 retained variants
  guitar
    clean   443 notes, MIDI 40-76, guitar-acoustic-clean
    detail  1060 notes, MIDI 40-88, guitar-acoustic-detail
```

### Retaining several variants per target

Use `vgt transcription` to keep and compare several candidates for one
target:

```sh
vgt transcription profile list "Song.RPP"
vgt transcription profile show guitar-acoustic-clean "Song.RPP"
vgt transcription variant add guitar --name clean --profile guitar-acoustic-clean "Song.RPP"
vgt transcription variant rename guitar clean --name "clean chords" "Song.RPP"
vgt transcription variant discard guitar clean "Song.RPP"
vgt transcription variant purge-discarded guitar "Song.RPP"
```

Refer to a variant by its label when unambiguous, or by its id. Variants
that differ only in cleanup share one detection pass. Variants are peers:
none is marked preferred. Reference MIDI tracks are recreated on every apply,
so edits to them are lost; make a working copy first.

### Project profiles

Define custom profiles in `Song.vgt-profiles.toml` beside the project. They
extend a built-in and list only overrides:

```toml
schema_version = 1

[profiles.my-clean-guitar]
target = "guitar"
extends = "guitar-acoustic-clean"
description = "Conservative chord-reading candidate"

[profiles.my-clean-guitar.cleanup.drop_harmonic_ghosts]
enabled = true
spectral_n_fft = 4096
spectral_hop_length = 512
```

Schema version 2 adds an analysis-only audio frontend. It feeds a cached,
processed WAV to the transcriber and never changes the stem:

```toml
schema_version = 2

[profiles.guitar-bandpass]
target = "guitar"
extends = "guitar-acoustic-clean"

[profiles.guitar-bandpass.audio_frontend]
stages = [{ type = "bandpass", low_hz = 70, high_hz = 5000, order = 4 }]
```

Run `vgt transcription profile validate "Song.RPP"`, then
`vgt transcription variant add guitar --name "my clean" --profile
my-clean-guitar "Song.RPP"`. Unknown keys, wrong targets, invalid bounds and
cycles are rejected. Cleanup stages always run in canonical order. Changing a
detection setting reruns detection once; changing only cleanup reuses it.

### Guitar

Guitar defaults to `guitar-klapuri`, which needs the optional Essentia
dependency (`pip install "vgt[essentia]"`); without it, guitar transcription
fails with an install hint. Alternatives:

- `guitar-melodia` — Essentia's other multi-pitch algorithm.
- `guitar-harmonic` — Basic Pitch on a 50% harmonic HPSS input.
- `default` — raw, tuned Basic Pitch.
- `guitar-acoustic`, `guitar-acoustic-clean`, `guitar-acoustic-detail` —
  Basic Pitch profiles for acoustic guitar.
- `guitar-mt3` — see [MT3 profiles](#mt3-profiles-guitarbass-experimental).

### Bass

Bass uses pYIN, a monophonic pitch tracker that runs in-process with no
install or download. Basic Pitch fails on bass stems, turning sustained low
energy into a permanent chord; see
[bass-transcription-findings.md](bass-transcription-findings.md) for the
measurements.

The tracker splits repeated notes on one pitch where the energy restarts.
Tune it with `rearticulation_rise_db`: raise it if notes are split too often,
lower it if repeated notes merge, `0` turns splitting off.
`rearticulation_minimum_spacing_beats` (default 0.375) is the closest two
splits may fall. The supported range is 35–330 Hz, so a five-string low B or
lower drop tunings need their own profile:

```toml
[profiles.low-bass]
target = "bass"
extends = "bass-pyin"

[profiles.low-bass.detection]
minimum_frequency_hz = 25
maximum_frequency_hz = 280
rearticulation_rise_db = 1.2
```

pYIN profiles accept only `minimum_note_length_ms`, `minimum_frequency_hz`,
`maximum_frequency_hz`, `sample_rate_hz`, `frame_length`, `hop_length`,
`median_filter_frames`, `rearticulation_span_frames`,
`rearticulation_rise_db` and `rearticulation_minimum_spacing_beats`.

It tracks one pitch at a time, so chords, double-stops and bleed collapse to
one note. `--mode bass=bass-basic-pitch` (or `bass-monophonic`) keeps the old
Basic Pitch path for comparison.

### Basic Pitch

To avoid building Basic Pitch's environment on first use, install it
separately and point `VGT_BASIC_PITCH_CMD` at the executable:

```sh
uv tool install --python 3.11 --with "setuptools<81" "basic-pitch[onnx]==0.4.0"
```

### Drums

Drum profiles:

- `raw` (default) — DrumScript's events, unfiltered.
- `hpss` — DrumScript on a 35% percussive HPSS input, with conservative
  cleanup: merges near-duplicate hits, nudges onsets up to ±30 ms toward
  clear transients, shapes velocity, and drops only clearly weak hits.
  `vgt transcription profile show hpss "Song.RPP"` prints its thresholds.
- `adtof` — the ADTOF backend (below).

Output is General MIDI percussion on channel 10: note names are instruments
(kick, snare, toms, hi-hat, crash, ride), not pitches. Simultaneous hits stay
separate notes. DrumScript gives no calibrated confidence, so status reports
`"confidence": null`.

vgt ignores DrumScript's own tempo detection. It snaps each onset to the
analyzed beat grid and writes the MIDI at the project tempo, so rerunning
tempo analysis re-transcribes drums.

Keep `raw` and `hpss` side by side and compare. `raw` is the more complete
audit trail; `hpss` reads more easily but may drop or nudge a real hit. Each
`hpss` note's JSON records its raw DrumScript data and what cleanup did to it.

```sh
vgt transcription variant add drums --name raw --profile raw "Song.RPP"
vgt transcription variant add drums --name hpss --profile hpss "Song.RPP"
```

To avoid building DrumScript's environment on first use (it pulls Torch and
Demucs), install it separately and point `VGT_DRUMSCRIPT_CMD` at it:

```sh
uvx --python 3.12 --from drumscript==0.1.6 drumscript --help
```

#### ADTOF (opt-in)

ADTOF is a second drum backend for comparison. It runs a pinned Torch model
in an isolated environment and needs its weights available locally. Output
uses the same MIDI and JSON format as DrumScript.

```sh
vgt transcription variant add drums --name adtof --profile adtof "Song.RPP"
```

To score either candidate against a hand-corrected reference (find variant
paths with `vgt status --json`):

```sh
uv run python scripts/drum_midi_score.py \
  /path/to/adtof.json /path/to/corrected-reference.json --window-seconds 2
```

Compare onset F1 and median timing error using the same reference and window
for both.

### MT3 provisioning

MT3 is used by the `guitar-mt3`/`bass-mt3` profiles, `--mt3-review`, and
on-demand track transcription. Provision it once:

```sh
vgt transcription backend provision mt3
```

This clones [the MT3 fork](https://github.com/mrkkucharski/mt3), verifies the
pinned commit, builds its isolated environment from its `uv.lock`, and
downloads the pinned checkpoint. Nothing else in vgt downloads MT3; features
that need it report the command above if it's missing.

- **Requirements:** Apple Silicon macOS, Python 3.11, a compatible `uv`, and
  `ffmpeg` on `PATH`.
- **Location:** `~/Library/Caches/vgt/mt3` (override with
  `VGT_MT3_CACHE_DIR`). Expect a real download and disk use.
- **Re-running:** verifies the checkpoint and does nothing if it's intact;
  repairs or resumes otherwise. `--force` rebuilds and redownloads.
- **Removal:** delete the cache directory.

### MT3 profiles (guitar/bass, experimental)

```sh
vgt transcription variant add guitar --name mt3 --profile guitar-mt3 "Song.RPP"
vgt transcription variant add bass --name mt3 --profile bass-mt3 "Song.RPP"
```

`guitar-mt3` accepts only `guitar` and `bass-mt3` only `bass`. Both feed the
raw stem to MT3 with no cleanup and keep one track from its output:

1. Drop every drum-channel track.
2. Drop every named track whose GM program is outside the target's family.
3. Merge the remaining named tracks into one candidate. MT3 often splits one
   part across programs, such as clean, overdriven and distortion guitar.
4. Keep whichever candidate has the most total note duration: the merged one
   or one of the unnamed tracks, which are never merged.

Both use the `replay12s_checkpoint_1290000` guitar-pilot checkpoint
(rhythm-free, no pitch bends) with a 1536-frame (~12.3 s) window and no
lookahead. `vgt transcription profile show guitar-mt3` prints the full pinned
identity.

**Limitation:** an unnamed track, or a second same-family instrument such as
another guitar, can end up in the variant. Treat these as experimental
comparisons; see `docs/instrument-transcription-findings.md`.

## On-demand single-track transcription

`vgt_transcribe_track.lua` transcribes any one selected track (a stem, a raw
recording, a `[work]` edit) as a background job, without the terminal. It
needs a project that has been initialized and analyzed (for the tempo).

1. Select one unmuted, non-`[vgt]` track and run `vgt_transcribe_track.lua`.
2. **Pick an instrument.** Guitar or bass families are offered when the track
   name suggests one; otherwise a list of common instruments. "Other" takes a
   raw GM program (0–127).
3. **Pick a method:**

   | Method | What it does |
   | --- | --- |
   | MT3 (default) | Merges every predicted note onto the chosen GM program. |
   | `guitar-klapuri` | Essentia Klapuri (needs `vgt[essentia]`). |
   | `guitar-melodia` | Essentia Melodia (needs `vgt[essentia]`). |
   | Basic Pitch | Plain Basic Pitch, no cleanup. |

   Only MT3 uses the chosen program; the others use it just as the track
   label.
4. Confirm. The track renders and the job runs in the background.
5. Finished jobs import automatically for a few minutes afterwards; run
   `vgt_get_transcription.lua` to import any later. The result is a new
   `<source name> (<method>)` MIDI track at the project tempo, and you get a
   system notification.

The result track is yours, like a `[work]` copy: apply never touches it. Job
state lives in `vgt/<stable-id>/track-jobs/<job-id>/status.json`.

## Working copies and promotion

**Create working copy** (`vgt_create_working_copy.lua`): select one or more
tracks (reference MIDI, `[vgt] Chords`, `[vgt] Key`, anything) and run it. Each
is duplicated into `[work]` as an editable copy that analyze, apply and sync
never touch. MIDI copies are fully detached from the source. If a selected
track's MIDI is pooled with another item, un-pool it first.

**Promote** (`vgt_promote_working_copy.lua`): select `[work]` copies and run
it. They move into `[clean]`, are renamed `[clean] …`, and become plain
user-owned tracks with their items and FX intact.

Both actions refuse, changing nothing, if the `[clean]`/`[work]` folder
structure was altered by hand. Delete unwanted copies with normal REAPER
commands. Renaming a copy so it no longer starts with `[work]` makes it an
ordinary track that promotion ignores.

## Guarantees

- vgt never changes your own tracks, items or regions, or anything inside
  `[clean]` and `[work]`.
- Re-running initialize or analyze never duplicates managed tracks, regions
  or stems.
- Synced section corrections and promoted `[clean]` tracks survive analysis
  and apply.
- Paid LALAL work happens only when missing or explicitly confirmed; plain
  `--force` never spends credits.
- `vgt status` is read-only and never shows the license key.

[verification-checklist.md](verification-checklist.md).
